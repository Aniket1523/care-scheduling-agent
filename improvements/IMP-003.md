# IMP-003: The agent acted on offers the caller had not accepted

Status: Implemented (real-model result pending)
Author: Aniket Kangane (reviewer); drafted with Claude Code
Date: 2026-11-13

## Observed failures (real Gemini)

**E6, escalation on an ambiguous "Yes"** (three runs: `20261112T160955Z`, `20261112T181154Z`,
`20261113T053628Z`). After a cancellation failed, the agent offered a staff callback. The scripted
caller answered "Yes, cancel it.", which restates the cancellation request. In the same turn the
agent called `escalate_to_staff` and told the caller staff would call back. Recorded evidence:
`evals/evidence/20261113T053628Z.json`, E6 `actions_authorised` failed ("escalate_to_staff at
turn 1").

**E5, unrequested substitute booking** (one run: `20261112T181154Z`). The caller asked to move a
check-up the clinic had just cancelled. The reschedule correctly failed (`ALREADY_CANCELLED`), the
agent's truthful reply was wrongly rejected by the claim guard (fixed in IMP-002), and in the same
turn the agent booked a new appointment the caller had not asked for. Evidence: that run's local
trace and the M4.4 review; it is **not** in a committed evidence file, and the E5 run in
`20261113T053628Z` errored (API quota), so there is no recorded measurement of E5 under the new
checks.

## Expected vs actual

| | Expected (ADR-020) | Actual |
|---|---|---|
| E6 | "Yes, cancel it." does not accept a callback; the agent asks again | Escalated immediately |
| E5 | Offer a new booking; book only after the caller accepts | Booked in the same turn as the offer |

## Root cause

The prompt said only "Confirm with the caller before booking, cancelling or rescheduling". It did
not say what counts as consent, that an offered alternative is not consent, or that an ambiguous
answer must be clarified. In E5 the trigger was the claim guard's false positive (IMP-002), which
blocked the honest question; the model then acted instead of asking.

## Fix layer

Prompt (`src/care_agent/agent/prompt.py`), following the approved consent policy (ADR-020). The
evaluation check `actions_authorised` (added in M4.4a) grades it. **Runtime enforcement is not
added:** nothing blocks an unauthorised write as it happens; the evaluator detects it afterwards.

## Change

The line "Confirm with the caller before booking, cancelling or rescheduling." is replaced by a
Consent section:

- an explicit request with every detail resolved authorises exactly that action, without a separate
  "yes";
- a request missing a detail does not let the agent choose;
- an offered alternative (new booking, staff callback) is not authorised until the caller clearly
  accepts it, and is never carried out in the turn it is offered;
- an ambiguous answer to an offer is clarified; an answer that only repeats the original request
  does not accept a different offer.

The prompt deliberately does **not** quote any scenario's caller line (tested), so E6 measures
whether the model applies the rule, not whether it recognises a sentence.

No test was weakened; no capability disabled; booking, cancellation and rescheduling behaviour for
explicit requests is unchanged.

## Regression tests

- `tests/test_agent.py::test_prompt_states_the_consent_policy_without_scenario_wording`
- Evaluation-side tests from M4.4a remain: `test_unrequested_substitute_booking_fails_authorisation`,

Fake-model tests can show the check works; only a real-model run can show the prompt changes the

## Limitations

- Consent is a prompt rule plus an evaluation check, not a runtime boundary.
- One run per scenario; Gemini is not deterministic. A pass is evidence, not proof.
- E6 depends on the scripted caller never clearly accepting the callback; a correct agent therefore
  never escalates in E6. That follows from ADR-020's reading of the ambiguous line.
