# IMP-004: A repeated callback request was reported as a new escalation

Status: Verified (real-Gemini E2 pass in two runs)
Author: Aniket Kangane (reviewer); drafted with Claude Code
Date: 2026-11-13

## Observed failure (real Gemini, E2)

Luis asks for a staff callback (turn 0), then "Can you make sure someone really calls me back?"
(turn 1). The injected `error_after_commit` on the first escalation was handled correctly: the
retry with the same `action_id` replayed it, and the EHR held **one** escalation. But on turn 1 the
agent called `escalate_to_staff` again and the tool answered `{"status": "ok", "data":
{"escalation": "open"}, "action_id": <new>, "verified": true}`.

- Run `20261112T181154Z` (local trace): agent said "I've sent an urgent note to the clinic staff";
  ledger: two verified escalation actions, one record.
- Run `20261113T053628Z` (recorded: `evals/evidence/20261113T053628Z.json`): agent said "I've
  highlighted your request to the team"; E2 failed `escalation_actions_match_records` and
  `actions_authorised`.

Nothing new was stored for the second request, so "urgent note" and "highlighted" were not true.

Separately, the M4.4 review probe found that a lost race between two requests for the same call
surfaced as a raw `sqlite3.IntegrityError`, which the tool did not catch (the database constraint
itself did prevent a duplicate).

## Expected vs actual

| | Expected | Actual |
|---|---|---|
| Repeat request | Report the existing request; no new action, no write | New `action_id`, `verified: true`, an idempotency row written |
| Ledger | One verified escalation action per escalation | Two verified actions, one escalation |
| Lost race | "Already requested" | `sqlite3.IntegrityError` out of the tool |

## Root cause

`service.create_escalation` returned the existing open escalation for a new action, but did not
say so, and recorded an idempotency row for the new action. `ToolRunner.escalate_to_staff` therefore
treated every successful call as a new, verified escalation. The insert did not handle the
unique-index violation.

## Fix layer

EHR service (`src/care_agent/ehr/service.py`) and escalation tool (`src/care_agent/agent/tools.py`);
grading (`src/care_agent/evals/grading.py`).

## Change

- `create_escalation` returns `EscalationOutcome(escalation, created)`, in this order:
  1. replay: an `action_id` that already created an escalation returns it with `created=True`
     (so a retry after an error after commit is never reported as a repeat);
  2. a new action for a call with an open escalation returns it with `created=False` and writes
     nothing: no escalation, no idempotency row;
  3. otherwise insert; if the insert violates `ux_one_open_escalation_per_call` (a concurrent
     request won), return the winner with `created=False`. Any other database error propagates.
- `escalate_to_staff` returns `{"escalation": "created", "escalation_id": ...}` with `action_id`
  and `verified: true` only when an escalation was created, and records the escalation ID as the
  ledger `record_id`. Otherwise it returns `{"escalation": "already_requested", "escalation_id":
  ...}` with no `action_id` and guidance not to claim a new or urgent note. If every attempt fails
  with an uncertain outcome, a read of the open escalation is interpreted against the one open
  before the attempts.
- Prompt: one line on `already_requested` (part of the IMP-003 consent section).
- Grading: generic `ledger_matches_ehr`: every verified action has a `record_id`, the record shows
  the change, and no two verified actions claim to have created the same record.
- The strict expected failure on scripted E2 is removed: it now passes.

## Regression tests

- `tests/test_agent.py`: `test_repeat_escalation_request_reports_already_requested_without_an_action`,

- Mutation check: forcing `created=True` makes the repeat-request test and scripted E2 fail.

## Limitations

- The second request's reason is not stored. If the clinic wants follow-up notes on an open
  escalation, that needs a notes table; out of scope.
- Whether Gemini then words its reply honestly ("already with the team") is prompt-driven; a
  free-text overstatement such as "urgent note" is not detectable by the wording patterns.
