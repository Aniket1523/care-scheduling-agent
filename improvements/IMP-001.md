# IMP-001: Successful identity check was reported to the model as `verified: false`

Status: Verified
Author: Aniket Kangane (reviewer); drafted with Claude Code
Date: 2026-11-12

> **Scope of the evidence.** This failure was found in a manual real-Gemini conversation, **before**
> the formal evaluation existed. The six-scenario baseline (6/6) was recorded **after** this fix.
> This record therefore does not claim a measured 0/6 -> 6/6 improvement. The "before" is the observed
> real conversation; the "after" is a real-Gemini retest of the same situation plus the later
> formal runs.

## Observed failure

- **Scenario:** F3: an existing patient calls from her spouse's phone. Manual session
  `python -m care_agent chat --phone +15550100002` (Luis Garcia's number) on the demo EHR.
- **Caller:** "I'd like to book an appointment.", then "Maria Garcia, 14 March 1985."
- **Agent replied:** "I couldn't find an existing patient record with the details Maria Garcia,
  14 March 1985. Are you a new patient at our clinic?"
- **Diagnostic evidence** (owner's run with `CARE_AGENT_DEBUG_TOOLS=1`; console output, not saved to
  the repository):
  - Gemini called `verify_identity(first_name="Maria", last_name="Garcia", date_of_birth="1985-03-14")`.
  - The EHR's `resolve_identity` returned `status=matched, method=name_dob, candidate_count=1,
    patient_id=pat_maria`.
  - The tool result sent back to Gemini was:
    `{"status": "ok", "verified": false, "action_id": null, "data": {"identity": "verified", "first_name": "Maria"}}`.

## Expected vs actual

| | Expected (ADR-019) | Actual |
|---|---|---|
| Identity | Maria verified by first name, last name and DOB, despite Luis's phone | The EHR verified her, but the agent told her no record existed |
| Next step | Continue to booking for `pat_maria` | Offered new-patient registration: the path that, if followed, creates the F3 duplicate record |

## Root cause

Two pieces of the M2 code combined to give the model a contradictory signal:

1. `ok()` in `src/care_agent/agent/tools.py` **always** added `"verified": <value>` (default `False`)
   and `"action_id"` to every successful result. Those fields were designed for **write** results,
   where `verified=true` means a fresh EHR read confirmed the change. Reads and `verify_identity`
   never set them, so every successful lookup said `verified: false`.
2. `SYSTEM_PROMPT` in `src/care_agent/agent/prompt.py` told the model to "say something happened
   only if its tool result had verified=true".

Gemini followed the prompt: it read `verified: false` as "not verified" and ignored
`data.identity = "verified"`.

**Layers ruled out by the evidence:** Gemini's tool choice and arguments (correct, ISO date), date
parsing, the dispatcher, EHR identity resolution, conversation state (`verified_patient` was set to
Maria), and how tool results are appended to the history.

**Why the tests missed it:** the scripted fake model only read `verified` on write results, never on
identity results, so the contradiction was invisible to every fake-model test.

## Fix layer

Tool result contract (`agent/tools.py`), plus the prompt text that explains it (`agent/prompt.py`).
No change to identity matching, the EHR, the ledger or the claim guard.

## Change

- `ok()` / `failed()`: `action_id` and `verified` are included **only on write results** (register,
  book, cancel, reschedule, escalate). Reads omit both fields entirely.
- `verify_identity` reports an explicit `identity_status` on every outcome:
  - success: `{"status": "ok", "data": {"identity_status": "verified", "first_name": ...}}`;
  - failure: `identity_status` is `not_found`, `ambiguous` or `verification_required` (added by
    `_identity_failed()`), or `not_checked` when the date of birth cannot be read (added directly to
    the unreadable-DOB result).
- Prompt: `identity_status: "verified"` means the caller is verified; `verified=true` applies only to
  the five tools that change something, which are named.
- Write operations are unchanged: `verified=true` still only after an authoritative EHR read-back,
  and the OutcomeLedger and claim guard semantics are unchanged.
- Docs: the CLAUDE.md convention line, an ADR-010 clarification in `docs/design/DECISIONS.md`, and
  `docs/AI_USAGE.md` ("Where AI was wrong") record the corrected contract.

Confirmed: no test was weakened, no capability disabled, ADR-019 unchanged (phone is still only a
hint; nothing registers automatically; no fuzzy matching).

**Commit:** the fix shipped inside `7582822 feat(m2): implement Gemini scheduling agent`, together with
the agent itself. The faulty version was found and fixed before M2 was committed, so there is no
separate "before" commit in the history.

## Regression tests

In `tests/test_agent.py`, all network-free, using the seeded demo EHR and Luis's phone:

| Test | Proves |
|---|---|
| `test_successful_identity_result_is_unambiguous` | Gemini's exact arguments give exactly `{"status": "ok", "data": {"identity_status": "verified", "first_name": "Maria"}}`, with no `verified` key, and `pat_maria` is stored in state |
| `test_identity_result_seen_by_the_model_is_unambiguous` | Through the agent loop, the result the model receives says verified and has no `verified: false` |
| `test_patient_scoped_tools_use_the_verified_patient` | After verification, `list_my_appointments` and `book_appointment` act for `pat_maria`, not Luis |
| `test_failed_identity_lookup_does_not_verify_anyone` (2 cases) | A wrong DOB (`not_found`) or an ambiguous date (`not_checked`) verifies nobody; patient tools stay locked |
| `test_ambiguous_identity_is_reported_explicitly` | Duplicate name + DOB records give `identity_status: "ambiguous"`, nobody verified |
| `test_read_results_carry_no_write_confirmation_fields` | `list_services` and `find_slots` carry no `verified` or `action_id` |

Checked to fail on the old code: with the original `ok()` restored, the three contract tests fail,
matching the real-run failure. All 7 cases pass on the current code.

## Limitations

- **The "before" is not a formal scenario run.** It is one manual conversation, and the diagnostic
  output was read from the console, not saved. The formal evaluation was built and baselined after
  the fix, so the before/after comparison is qualitative: same situation, same real model, opposite
  outcome.
- **One run each.** Gemini is not deterministic; the passing retest and the 6/6 baseline are
  evidence, not proof that the failure can never recur.
- **`runs/` is git-ignored.** The traces cited above exist on the development machine only;
  `evals/baseline.json` is the committed record of the 6/6 result.
- **A related but separate change.** An earlier change, made before this evidence existed, widened
  date-of-birth parsing at the tool boundary. The real diagnostics later showed Gemini had sent an
  ISO date, so that change was **not** the fix for this failure. It is kept because it is correct
  behaviour, and tested, but it is not claimed as part of IMP-001.
- **Two observations from the same traces, outside this record's scope:**
  - In both E3 runs Gemini booked in the turn where the caller named the slot, before the caller
    said "Yes, please book it". The prompt asks for confirmation first. The scenario's EHR checks do
    not grade this.
  - In turn 2 Gemini said the appointment "is already booked" without confirming an action ID. The
    claim was true (the booking existed), but the success-wording backstop does not recognise
    "already booked": a real example of the documented detector blind spot.

  Each would be a candidate for its own improvement record if judged worth fixing.
